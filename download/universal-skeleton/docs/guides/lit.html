Lit & Web Components

universal-skeleton is itself built on Web Components, so Lit is a natural host. The one thing to know: Lit renders into the shadow DOM — the scan engine works there too, you just point it at the right element.

Install

npm install universal-skeleton

Or skip npm entirely and use the CDN module — it registers <skeleton-screen> globally:

import 'https://unpkg.com/universal-skeleton/dist/index.esm.js';
// note: the ESM build exports the API; the IIFE build sets window.UniversalSkeleton

Scanning inside shadow DOM

scan() works on any element — including elements inside a shadow root. The overlay is appended inside the scanned element, so everything stays self-contained:

import { LitElement, html, css } from 'lit';
import { SkeletonLoader } from 'universal-skeleton';

export class ProfileCard extends LitElement {
  static properties = {
    profile: { state: true },
  };

  private handle = null;

  async firstUpdated() {
    // firstUpdated = the DOM now exists with real geometry — scan here.
    const card = this.renderRoot.querySelector('.card');
    this.handle = SkeletonLoader.scan(card, { effect: 'wave', theme: 'auto' });

    this.profile = await SkeletonLoader.while(
      fetch('/api/profile').then(r => r.json()),
      card,
      { minDuration: 500 },
    );
  }

  disconnectedCallback() {
    super.disconnectedCallback();
    this.handle?.destroy();
    this.handle = null;
  }

  render() {
    return html`
      <div class="card">
        <h2>${this.profile?.name ?? 'Loading…'}</h2>
        <p>${this.profile?.bio ?? ''}</p>
      </div>
    `;
  }
}
customElements.define('profile-card', ProfileCard);
Why scan an inner element and not the host? Overlay positioning is relative to the scanned element — scanning .card keeps the skeleton clipped to the card, even if your host element has padding or a different border radius.

Composing with <skeleton-screen>

Because <skeleton-screen> is a standard custom element, you can drop it straight into a Lit template — no scanning code at all:

static properties = { loading: { type: Boolean } };

render() {
  return html`
    <skeleton-screen ?loading=${this.loading} effect="pulse" theme="auto">
      <article class="order">…real markup…</article>
    </skeleton-screen>
  `;
}

The component reacts to the loading property/attribute, overlaying the skeleton while it is truthy. Changing effect, theme, color, highlight-color, duration or radius re-syncs live.

For library & design-system authors

You can reuse the engine inside your own components:

  • registerSkeletonScreen('my-skeleton') registers the same implementation under your own tag name (guarded, subclassed per alias).
  • injectStyles() is idempotent — call it in connectedCallback() if your component scans on its own.
  • SKELETON_CSS exposes the raw stylesheet string; append it to your shadow root (adoptedStyleSheets) when you do not want document-level styles.
  • The EFFECTS / THEMES arrays are exported for building pickers and validators.
import { css, unsafeCSS } from 'lit';
import { SKELETON_CSS, EFFECTS } from 'universal-skeleton';

class MyCard extends LitElement {
  static styles = [css`${unsafeCSS(SKELETON_CSS)}`, css`/* yours */`];
}

Gotchas

  • Scan after render, not in connectedCallback. The shadow DOM may be empty until Lit's initial render completes — firstUpdated() is the reliable hook.
  • Hidden content produces no blocks. Parts rendered under hidden or display:none are skipped; re-scan (or handle.update()) when they become visible.
  • Slotted content is light DOM. To skeletonize projected children, scan the host's light-DOM children from the parent page, or scan inside the slot's assigned elements.
  • Global registry is global. skeleton-screen is registered once per document; defining your own element with the same tag throws — use registerSkeletonScreen('alias') instead.
