React & Next.js

Scan in useEffect, destroy in the cleanup function — that is the whole integration. Works in Create React App, Vite and the Next.js App Router alike.

Install

npm install universal-skeleton

TypeScript declarations ship with the package — no @types install needed.

Pattern 1 — scan on mount, destroy on cleanup

The handle lives exactly as long as the effect run. React calls the cleanup on unmount and before every re-run, so nothing leaks:

import { useEffect, useRef } from 'react';
import { SkeletonLoader } from 'universal-skeleton';

export function ProfileCard({ userId }: { userId: string }) {
  const ref = useRef<HTMLElement>(null);

  useEffect(() => {
    if (!ref.current) return;
    const handle = SkeletonLoader.scan(ref.current, {
      effect: 'wave',
      theme: 'auto',
    });
    return () => handle.destroy();        // ← the important line
  }, [userId]);

  return (
    <section ref={ref}>
      {/* real markup — React renders your "empty/loading" state here */}
      <h2>Loading profile…</h2>
    </section>
  );
}

Pattern 2 — SkeletonLoader.while() with data fetching

const [user, setUser] = useState<User | null>(null);
const ref = useRef<HTMLElement>(null);

useEffect(() => {
  let alive = true;
  const promise = fetch(`/api/users/${userId}`).then(r => r.json());

  SkeletonLoader.while(promise, ref.current!, { minDuration: 500 })
    .then((u: User) => { if (alive) setUser(u); });

  return () => { alive = false; };   // while() destroys the skeleton itself
}, [userId]);
  • while() restores the UI even when the fetch fails, so no catch bookkeeping is needed for the skeleton.
  • minDuration prevents flashing on fast responses.

Pattern 3 — the <skeleton-screen> element

For purely declarative spots, the Web Component needs no effect lifecycle at all:

<skeleton-screen loading={loading ? '' : undefined} effect="pulse">
  <article className="product">…</article>
</skeleton-screen>
React version note. React 19 sets attributes on custom elements correctly. On React 18 and older, boolean props on custom elements are unreliable — pass the attribute as a string (loading="") or remove it (loading={undefined}) as shown above.

Next.js (App Router)

  • Importing the package on the server is safe — the module is SSR-guarded. But scanning is DOM work, so keep it in client components.
  • Add 'use client' at the top of any component that calls scan() / while():
'use client';

import { SkeletonLoader } from 'universal-skeleton';
// …the rest is identical to Pattern 1 or 2
  • Server Components: render your loading state as a Server Component; scan it from a small client wrapper when it hydrates.
  • React Server Components streaming: if you already use <Suspense>, you can combine both — Suspense swaps in your fallback markup, and scanning that same markup keeps the geometry identical when data swaps in.

StrictMode & concurrent rendering

React 18/19 StrictMode intentionally mounts → unmounts → remounts effects in development. The pattern above is already correct: the first cleanup destroys the first skeleton, and a fresh scan() replaces anything left over. Scanning the same element twice never stacks overlays.

Gotchas

  • Scan rendered DOM, not lists that change length. If rows are added after scanning, call handle.update() (or re-run the effect by depending on the row count).
  • Don't unmount what you scanned mid-flight. If the scanned node can disappear, always destroy via cleanup — the handle holds no global references, but destroying removes the overlay immediately.
  • Keep effects cheap. scan() is a single layout pass over the subtree — fine on mount, not something to run on every keystroke.
